bruster

A native webview browser driven by an agent over JSON lines on stdio. No Chromium download, no Node, one process under 1 MB.

bruster controls the engine the operating system already ships - WKWebView on macOS, WebKitGTK on Linux and WebView2 on Windows - through a small Rust binary built on wry. Agents drive it with one JSON object per line, or over the Model Context Protocol with --mcp.

Overview

bruster starts with its native protocol on stdout and reads commands from stdin. It is one process - no bundled browser, no runtime - and it speaks both a line-oriented JSON protocol and the Model Context Protocol. The same binary works for a scripted scrape, a test harness, or an agent tool stack.

  • Native engine. WKWebView, WebKitGTK 4.1 and WebView2, selected at build time.
  • Small. A single release binary around 1 MB; no separate browser download.
  • Complete. Navigation, DOM snapshots, forms, screenshots, cookies, tabs, network and console logs.
  • Portable. Prebuilt for macOS (arm64, x86_64), Linux (x86_64, arm64) and Windows (x86_64).
  • Agent-ready. --mcp exposes every method as a tool; page events arrive as notifications.

Installation

The install script downloads the build for this OS and CPU into ~/.local/bin:

curl -fsSL https://raw.githubusercontent.com/aliilyas/bruster/main/install.sh | sh

Prebuilt archives for every platform are attached to the releases page. From source, with a Rust toolchain:

cargo build --release
Linux runtime. WebKitGTK 4.1 is required (apt install libwebkit2gtk-4.1-0, apk add webkit2gtk-4.1, dnf install webkit2gtk4.1). Without a desktop session, bruster re-runs itself under xvfb-run -a when no DISPLAY is set.

Quickstart

Send one JSON object per line to stdin; read results and events from stdout:

$ bruster
→ {"id":1,"method":"navigate","params":{"url":"https://example.com"}}
← {"event":"load","tab":1,"url":"https://example.com/"}
← {"id":1,"result":{"url":"https://example.com/"}}
→ {"id":2,"method":"snapshot"}
← {"id":2,"result":{"url":"...","title":"Example Domain","elements":[{"ref":"e1","role":"heading","name":"Example Domain"}]}}
→ {"id":3,"method":"click","params":{"ref":"e1"}}
← {"id":3,"result":null}

Command-line usage

bruster [--mcp] [--hidden|--visible] [--quiet] [options]
--mcpspeak Model Context Protocol on stdio instead of the native protocol; implies --hidden
--hidden / --visiblepark windows off-screen / show them
--quietsend stderr to /dev/null; mutes GL, ALSA and GTK noise
--viewport WxHinitial window size, default 1280x800
--user-agent UAoverride the user agent
--profile DIRpersistent cookies and storage
--proxy URLhttp://host:port or socks5://host:port
--init-script FILEJavaScript run in every page before its own scripts
--insecureignore TLS errors (Linux only)
--no-imagesdo not load images; pages load about 30% faster (Linux only)

Model Context Protocol

With --mcp, every method below becomes a tool, and page events are delivered as notifications/message. Buttons remain hidden unless --visible is added.

opencode, Claude Desktop, Cursor, Windsurf and Zed share one shape:

{ "mcpServers": { "bruster": { "command": "bruster", "args": ["--mcp", "--quiet"] } } }
claude mcp add bruster -- bruster --mcp --quiet
codex mcp add bruster -- bruster --mcp --quiet

VS Code uses a servers key:

{ "servers": { "bruster": { "type": "stdio", "command": "bruster", "args": ["--mcp", "--quiet"] } } }

Native protocol

One JSON object per line, in both directions. A request carries id, method and optional params; the reply carries the same id with a result or error. Elements are addressed by {"selector": "css"} or by a ref from the last snapshot. With format: "text" a snapshot renders as one line per element, about 45% smaller than JSON:

https://example.com/
Example Domain
e1 heading "Example Domain"
e2 text "This domain is for use in..."
e3 link "Learn more" href=https://iana.org/help/example-domains
e4 checkbox "Remember me" checked=false

A selection of the available methods. The full table, with every parameter and result, is in the repository README.

Events

Unsolicited messages use an event field: ready, navigating, load, tab_opened, tab_closed, dialog, tls_error, load_failed and download.

Limitations

  • Input is synthetic DOM events (isTrusted is false): no :hover styles, no native select popups, no OS shortcuts.
  • Network and console logs are in-page; they carry no request bodies and reset on navigation. Use --proxy for real interception.
  • Cross-origin iframes are out of reach; same-origin iframes and open shadow roots work.
  • data: and file: pages load, but in-page calls get no reply - serve pages over localhost instead.
  • Native file choosers are not intercepted; use upload.
  • Without --profile, cookies and storage live for one session.
  • On Windows (WebView2), screenshot has no clip and the Linux-only flags do nothing.

Development

bin/bruster runs the development build from a checkout. tests/run_all.sh [--rounds N] [--no-e2e] runs the whole cycle: build, unit tests, the smoke and edge suites, a leftover-process check, the MCP launch check and the public-site end-to-end tests. On Linux, run it under xvfb-run -a. CI builds and tests every platform and publishes release archives on a v* tag.
