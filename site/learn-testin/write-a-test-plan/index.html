A test plan can be just a few lines long. Its job is to make your intention clear before you choose commands or write a file.

Use a notebook or a plain document for this lesson. Write in ordinary language. If another person can follow your steps and decide whether the result is correct, you have a useful plan.

Start with a specific question

For our first form test, the question is: Can someone enter a name and project and get the correct receipt? We will leave the optional choices at their defaults. That gives us a small first check.

Do not try to test every feature in one long journey. If a long test fails near its beginning, you may learn nothing about the later steps. Short tests make the cause of a failure easier to locate.

Write these four lines

Name: A valid project produces a receipt.

Start: Open the practice page with no previous receipt.

Do: Enter Ada Lovelace and Bruster, then press Create smoke test.

Check: The heading says “Smoke test created for Bruster”.

The name should describe the behavior, not just say “Test 1”. Good names make a list of results easier to read. When “A valid project produces a receipt” fails, a colleague already knows which behavior needs attention.

The values matter too. “Enter some information” leaves too much to guess. Use a fixed practice name and project so the expected receipt is predictable.

Add one case where the user makes a mistake

A test case is one situation you want to check. A complete form and a form missing a project are two different cases. A website needs to handle both.

Name: A missing project blocks submission.

Start: Open a fresh practice page.

Do: Enter Ada Lovelace, leave Project empty, and press Create smoke test.

Check: No receipt appears, and Project is marked invalid.

This is often called a negative test: it deliberately uses input that should be rejected. A negative test passes when the page rejects that input correctly. The word “negative” does not mean the test itself should fail.

Separate facts from guesses

You know the practice form requires a project because the field has a required rule and the browser blocks an empty submission. You should not invent another rule, such as “project names must contain at least ten characters”, unless the application actually requires it.

On a real project, ask the person responsible for the feature what should happen. A test is most useful when it checks behavior the team has agreed on. It should not quietly turn your personal preference into a requirement.

Likewise, this demo produces a receipt on the page. It does not store a project on a server. Your plan should say “a receipt appears”, rather than claim that a database record was created.

Choose a first set of checks

For this course, a sensible small plan is: the page opens, a valid form succeeds, a missing project is rejected, the choices reach the receipt, and a new submission updates the receipt. You will build toward those five checks in the final project.

You can keep other ideas in a separate list. Thinking of more cases is valuable, but you do not have to automate them all immediately.

Write a case for turning Include screenshots on. Use the four labels Name, Start, Do, and Check. Include the exact words you expect in the receipt.

You can explain a small case without mentioning a command. The browser instructions you learn next will express that same plan.
