Each test should establish its own starting point. It should not need another test to run first or leave a page in a particular state.

Imagine a first test creates a receipt and a second test tries to edit it. If the first test fails, the second one also fails, even if editing works correctly. You now have two failures but only one underlying problem.

Fresh browsers make the boundary clear

Bruster starts a fresh browser process and profile for each named test. A profile stores browser data, including cookies and other information saved by websites. A fresh profile gives the next test a clean starting point.

This also means the next test will not inherit an open page, filled fields, or a receipt. It needs its own navigation and preparation.

Actions within one test do share the same browser. That is why you can fill a field, click a button, and inspect the resulting receipt in one sequence. The fresh-start boundary is between named tests, not between every line.

Use before_each for repeated preparation

A before_each block is a list of steps Bruster runs before each test in that file. It is useful when several tests need the same initial page.

Know what belongs in shared setup

Put steps in before_each when every test in that file genuinely needs them. Opening the same page is a common example.

If one case must test an empty name field, filling the name in shared setup can make that case confusing. You would need to undo the setup. It may be clearer to fill the name only in cases that need a valid one.

For the choices example in lesson 12, both tests needed the name and project fields filled in, so putting those steps in shared setup was sensible. For required-field checks, filling the fields inside each test makes its intention easier to see.

Keep a complete journey together when it needs shared state

Some checks naturally need several related actions. To test a second submission replacing a first one, both submissions should happen inside the same test. The first submission establishes the state that the second part of that same case is meant to change.

That is different from relying on a separate named test. The preparation and the assertion stay together, so you can read the whole story in one place.

Run and rearrange the cases

macOS / Linux
./bruster test independent-tests.bru
Windows PowerShell
.\bruster.exe test independent-tests.bru

Expect two passes. You can swap the two complete test blocks and run again. They should still pass, because neither depends on the other.

A file can have one before_each block. Keep it outside the test blocks and close it with its own end. Test names must be different within a file so the report can distinguish them.
