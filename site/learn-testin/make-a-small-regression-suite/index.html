The value of a useful test grows when you run it again after a change. A small, understandable collection is a good place to start.

A regression is a behavior that used to work but breaks after a change. A test suite is a collection of tests. A regression suite is a collection you repeat to check that important behavior still works.

Choose checks that answer real questions

For the practice form, you might choose the page-opening check, a valid submission, and the two required-field checks. Together, those cases tell you more than opening the homepage several times would.

On a real website, ask which failures would most interrupt the work people need to do. A sign-in page, a search function, or a form submission might deserve an early smoke test. The right choice depends on the application.

Keep a short note beside your suite: what each test covers and why it exists. If nobody can explain the purpose of a test, review it before adding more complexity.

Run several files in one command

Save the three files below in your practice folder. They are available individually in earlier lessons and together in the practice ZIP.

macOS / Linux
./bruster test first-check.bru form-submit.bru required-fields.bru --output routine-results
Windows PowerShell
.\bruster.exe test first-check.bru form-submit.bru required-fields.bru --output routine-results

Expect 4 passed, 0 failed: one test in the first file, one in the second, and two in the third. File count and test count are not necessarily the same.

Listing filenames explicitly works across these command shells. You may see examples using *.bru to mean all matching files, but not every shell expands that pattern in the same way.

If a valid test fails during a run, its later steps stop, but Bruster can continue with the next named test. Syntax errors are different: all input files are validated before browser execution begins.

Try a narrow browser window

A responsive layout adapts to the available screen width. You can run the same form check with a narrower viewport:

macOS / Linux
./bruster test form-submit.bru --viewport 375x640 --visible
Windows PowerShell
.\bruster.exe test form-submit.bru --viewport 375x640 --visible

The first number is the width and the second is the height, in viewport pixels. This checks the same form behavior in a narrower layout.

A narrow viewport is not a complete phone simulation. It does not change your operating system’s webview into a mobile browser or reproduce touch hardware. Use it as one useful layout check, and choose additional device testing when your project needs it.

Make a repeatable routine

  1. Open the intended website or start its preview server.
  2. Run the same small suite after an important change.
  3. Read every failure and preserve the relevant result folder.
  4. Check whether the problem is in the application, the test, or its environment.
  5. Update tests when an agreed requirement changes, and keep their names meaningful.

Bruster does not automatically rerun an entire failed test until it passes. Repeating a failing test can help investigation, but do not let an occasional success erase a failure you have not understood.

Where CI fits

Continuous integration, usually shortened to CI, is a service that runs checks after changes are pushed to a repository. It can run the same Bruster command on another computer and save its reports.

The basic idea is familiar: prepare the environment, start the website, run the tests, and read the result. Bruster returns exit code 0 for all tests passed, 1 for test/browser failures, and 2 for invalid inputs or report problems. CI uses that signal to mark a step successful or failed.

You do not need to configure CI to complete this course. When your local suite is useful, the CI walkthrough shows a concrete GitHub Actions example.
