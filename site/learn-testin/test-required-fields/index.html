A useful form should guide people when information is missing. A test can check that an invalid submission is blocked and that the user can fix the problem afterward.

Our practice form requires a name and project. Leaving one of those fields empty gives us a simple, repeatable invalid case. Remember that a test for invalid input should pass when the form correctly refuses it.

Try the behavior by hand first

  1. Open a fresh practice page.
  2. Enter Ada Lovelace as the name and leave Project empty.
  3. Press Create smoke test.
  4. Look for the browser’s required-field indication. Confirm that no receipt appears.
  5. Enter Bruster as the project and submit again. Now a receipt should appear.

The browser’s small validation bubble may look different on different computers or use a different language. Our test will check the field’s invalid state rather than the exact wording of that browser-provided bubble.

One new selector: :invalid

You already know that #project finds the project field. Adding :invalid narrows the selector to that field when its current value does not meet its rules.

#project:invalid therefore means “the project field, if it is currently invalid.” An empty required project field matches that description.

The command expect attached checks that an element matching a selector exists in the page. Used with this selector, it checks that the invalid field is present. It does not look for a particular popup message.

Two small tests

Download required-fields.bru ↓

{{required_fields}}

The first case leaves the name empty while providing a project. The second leaves the project empty, checks the rejection, then corrects the project and checks the successful receipt.

Keeping the two missing fields in separate cases helps locate a problem. If only the name requirement breaks, the test names will point you toward that field instead of reporting a vague form failure.

Why check both invalid state and the missing receipt?

The invalid selector confirms the field’s validation state. expect hidden "#result" confirms that the page has not shown a successful receipt for this attempt.

These are related observations, but they answer different questions. A field could be marked invalid while faulty application code still displays a success message. Checking the receipt helps catch that inconsistency.

The recovery steps matter too. A form that blocks invalid input but stays stuck after correction would be frustrating. The second case verifies that this user can continue after providing the missing value.

Run the required-field checks

macOS / Linux
./bruster test required-fields.bru
Windows PowerShell
.\bruster.exe test required-fields.bru

You should see two passing tests. A negative case passing is a good result: the form rejected the input it was supposed to reject.

Try it: add recovery for the name

At the end of the first case, fill the missing name with Ada Lovelace, click the button again, and check the project heading. Save and rerun the file.

Which assertion should you add?

After filling and clicking, use expect text "#result h2" "Smoke test created for Bruster". The project was already filled earlier in that same test.

Your new skill

You can test both “the form should accept this” and “the form should reject this”, and you can explain why both are useful.
