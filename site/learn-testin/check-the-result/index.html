Check the starting state

expect hidden "#result" checks that the receipt is hidden or absent before submission. This gives the test a clear starting condition. It should not begin by accepting a receipt from an earlier action.

Hidden and empty are different. A visible receipt with no words in it is not necessarily hidden. This command asks about visibility, not the amount of text.

Check that the result appears

After the click, expect visible "#result" checks that the result element is shown. This establishes that the receipt exists in a visible state on the page.

“Visible” here does not promise that the element fits inside the current screenshot. It may be farther down a long page. You might need to scroll to see it in your own browser or in a viewport-sized image.

Check the exact words when they matter

expect text compares the element’s text with the value you provide. Before comparing, Bruster removes spaces at the beginning and end of the page text and turns repeated spaces, tabs, and line breaks into single spaces. Write the expected text with single spaces between words. The words, capitalization, and punctuation must still match exactly.

We check the heading with #result h2 and the detail line with #result p. This avoids mixing those two messages with the small “LAST SUBMISSION” label elsewhere in the receipt.

The detail line in this test uses the default workflow, Navigation check, and the default checkbox state, Screenshots: off. The dots between the pieces are part of the text. Copy the complete expected line when you want an exact check.

Use a partial match for a partial requirement

Sometimes you only care about one piece of a longer message. In this example, the following assertion would check just the screenshot setting:

Alternative assertion when Include screenshots is unchecked
expect contains "#result p" "Screenshots: off"

expect contains looks for that piece of text inside the whole element. It does not require the whole message to match.

Choose it because a partial match expresses the requirement, not simply because an exact check failed. A very loose assertion can miss a real mistake. Checking only that the receipt contains “Smoke test” would not prove that it names the right project.

Your rule of thumb

Ask, “Could the website be wrong in the way I care about and still pass this assertion?” If the answer is yes, make the observation more specific.
